# Buoy on BEAM: the compiler and runtime contract

Status: the working contract for the BEAM runtime, 2026-10-16. It replaces the "now" decision of ADR 0001. Buoy no longer runs on Node, Bun, or V8, and the product has no Node or V8 dependency. Node appears only as a test oracle and as a benchmark baseline.

This file is the contract between the compiler (`crates/buoy-compiler`), the CLI (`crates/buoy-cli`), and the runtime (`runtime/`). Every name in this file is normative. A change to a name changes this file in the same commit.

## 1. Pipeline

`buoy run app.ts [args...]`:

1. The CLI resolves the module graph from the entry module. It follows relative imports (`./x.ts`, `./x.js`, `./x`, `./dir/index.ts`), relative re-exports (`export { a, b as c } from`, `export * from`, and `export * as ns from`), and library imports (section 11). Any other import is error `BUOY201`. A module exports its named declarations, and `export default` of a named function or class declaration exports it as `default`, which a default import reads. A re-export that names only types, such as `export { type Point } from "./types.ts"`, is erased.
2. The compiler parses each module with oxc, runs oxc semantic analysis, checks the Buoy subset (section 10), and lowers the module to one Erlang source file.
3. The CLI writes the Erlang files to `<project>/.buoy/build/src/`. The project root is the nearest ancestor directory of the entry that holds a `package.json`, or else the entry's directory.
4. The CLI starts one VM: `erl +Bd -noshell -noinput -mode minimal -boot no_dot_erlang -pa <runtime ebin> -eval "buoy_main:start()" -extra <build dir> <entry module> <entry path> <module,module,...> [args...]`, with `ERL_CRASH_DUMP_SECONDS=0`, so a VM that fails to boot leaves no `erl_crash.dump`. `-mode minimal` starts the kernel without distribution and without `inet_db`, which `buoy_ai_openai` adds to the kernel supervisor on its first request (section 14), and `no_dot_erlang` reads no `.erlang` file. The `erl` script searches for its root directory with shell commands on each start, so the CLI starts the VM with the root directory that the runtime cache recorded: when the real path of `erl` is `<root>/bin/erl`, it runs `<root>/erts-<version>/bin/erlexec` with the variables that the script sets, `ROOTDIR`, `BINDIR`, `EMU=beam`, and `PROGNAME=erl`, and else it runs `erl` with `ERL_ROOTDIR=<root>`, unless the environment sets `ERL_ROOTDIR`. On Unix, the CLI replaces its own process with the VM, so a signal to the CLI reaches the VM. `buoy_main:start/0` gives SIGTERM its default action, so SIGTERM ends the VM at once, and it sends the OTP reports to stderr, never into the output of the program. It reads these arguments with `init:get_plain_arguments/0`. It compiles each listed module whose source changed in the VM with `compile:file/2`, writes the `.beam` file and an MD5 stamp of the source to `.buoy/build/ebin/` through a temporary file and a rename, loads the module, starts the runtime with `buoy_app:start/2` (section 8), runs the entry module, and halts. One VM start serves both compilation and execution. Generated code that does not compile is a compiler bug: `buoy_main` prints the errors of `compile:file/2` and halts with status 2. Any other failure before the program runs, such as a build directory that is not writable, prints `buoy: cannot start the program: <reason>` and halts with status 1, so the VM leaves no `erl_crash.dump`.
5. The program ends when the top-level code of the entry module returns. Then the runtime stops every actor and halts with status 0. An uncaught error in top-level code prints `Uncaught <name>: <message>` to stderr and halts with status 1. A compile diagnostic prints `<path>:<line>:<column>: <code>: <message>` to stderr, and the CLI exits with status 2 before it starts the VM. An entry path that is not a file prints `buoy: cannot find the file <path>` and exits with status 2. The exit status is the status of the VM. A signal that ends the VM, such as SIGTERM, or the SIGINT of Ctrl-C (`+Bd` turns off the BREAK menu), ends the program as it ends Node, and a shell reports 128 plus the signal number.

The CLI embeds the runtime sources, `runtime/src/*.erl`, `*.hrl`, and `buoy.app.src`, through `crates/buoy-cli/build.rs`. On the first run, the CLI writes them to `$XDG_CACHE_HOME/buoy/runtime-<hash>/src/` (default `~/.cache/buoy/runtime-<hash>/`) and compiles them into `runtime-<hash>/ebin/` with `erlc`, with `buoy.app.src` copied to `ebin/buoy.app`, and writes `code:root_dir()` and the erts version of `erl` to `runtime-<hash>/release`, one on each line. A runtime without the `release` file starts `erl` as it is. It builds in a private directory and renames it into place, so concurrent first runs are safe, and a failed build removes the private directory. The hash is FNV-1a over the embedded file names and contents and the real path of the `erl` that runs the program, which names the OTP release in Homebrew, asdf, and kerl installations. The installed OTP compiles the runtime, so the `.beam` files always match the installed OTP release. An empty or relative `XDG_CACHE_HOME` is ignored, as the XDG Base Directory specification says. The build of the CLI fails when `runtime/src` holds no runtime sources. `BUOY_RUNTIME=<dir>` names a directory of compiled runtime `.beam` files that replaces the cache, for development. An empty `BUOY_RUNTIME` is unset, and a directory without `buoy_main.beam` is an error before the VM starts. The CLI finds `erl` on `PATH`, or uses `BUOY_ERL`, and finds `erlc` next to `BUOY_ERL` or on `PATH`.

`process.argv` is the list of binaries `[<<"buoy">>, EntryPath | Args]`, so `process.argv.slice(2)` is the program arguments, as in Node. `buoy run <entry> [args...]` passes each argument after the entry as it is, `--help`, `-h`, and `--` included. The CLI replaces each invalid UTF-8 sequence of an argument with one U+FFFD, as Node does. `buoy_main:start/0` stores `process.argv` in `persistent_term` under `{buoy, argv}`, and `buoy_rt:argv()` reads it. `buoy_main:start/0` also sets `standard_io` and `standard_error` to `{encoding, unicode}`, so output is UTF-8 under any locale, as with Node. `console.log` in an actor writes to the device of the top-level code, not through the group leader of the application. A write to a closed stdout, as in `buoy run app.ts | head -1`, is dropped, and the program goes on, as in Node.

`BUOY_MAX_MEMORY` caps the memory of the VM, in bytes with an optional `K`, `M`, `G`, or `T` suffix (default `4G`). `buoy_guard` gives every process a `max_heap_size` of the limit and stops the VM when `erlang:memory(total)` passes it: the VM prints `buoy: the program used more than <n> MiB of memory and was stopped; set BUOY_MAX_MEMORY to change the limit` and halts with status 1. Test runners that start many VMs at once set a smaller limit.

When `BUOY_RESULT_FILE` names a path, `buoy run` writes the facts of the run there as one JSON object, so a test runner reads no stderr ([testing.md](testing.md) section 3.1). `status` is the exit status. `diagnostics` lists the code of each compile diagnostic when the CLI stops at them. `uncaught` holds the `name`, `message`, and `code` of the value that reached the top of the program, each when it is a string, and `erlang` when the runtime made the error from an Erlang reason. A top-level `erlang` holds an Erlang reason that is not a JavaScript value, or the report of a VM that failed around the program, such as generated Erlang that does not compile. `buoy_main:finish/2` writes the file and halts. A VM that crashes or is killed writes no file. `buoy_compiler::compile_goal` parses every file of a program with one goal, a script or a module, for the test262 runner; the CLI uses the goal of each file extension.

`buoy [node options] <script> [args...]`, `buoy -e <code>`, and `buoy -p <code>` run as `node` does, with the reference semantics, so a program that starts `process.execPath` as node starts Buoy. A first argument that is no subcommand starts this form. Every argument before the script, or up to and including the code of `-e` or `-p`, is a node option; the CLI passes them to the VM as the JSON array of `-buoy_exec_argv <json>`, which `process.execArgv` holds. The code of `-e` compiles as the module `[eval].cjs` of the working directory, or `[eval].mjs` with `--input-type=module` or a line that starts with `import` or `export`; `-p` evaluates the code with indirect eval and prints its value at exit. For `-e` and `-p`, the CLI also passes `-buoy_eval true`, and `process.argv` holds no script. `buoy -` and `buoy` with no argument and a stdin that is no terminal run the text of stdin as `-e` runs its code; `-` stays `process.argv[1]`.

`buoy check app.ts` runs steps 1 and 2 and prints diagnostics. `buoy build app.ts` runs steps 1 to 3 and prints the paths of the Erlang files. Both exit with status 2 when there is a diagnostic.

`run`, `check`, and `build` take `--semantics value|reference` before the entry. `value`, the default, is sections 2 to 16 of this contract. `reference` is the JavaScript engine of [ADR 0003](../adr/0003-run-typescript-on-beam.md), which section 17 describes: objects live in a heap in each process and have identity, and promises run on a job queue in each process. It compiles one module, and it imports only `spawn` and `stop`, and the probes `heapStats` and `vmMemory`, from "buoy".

Every value has value semantics. A mutation changes the variable or the field that holds the value. Another variable that held the same value keeps the old one. This is the largest difference from JavaScript, and it is what isolates actors: a message cannot share mutable state, because no value changes in place.

Known differences from JavaScript. Each one is a documented limitation:

- `===` on arrays and objects compares contents, because values have no identity.
- Object keys iterate in Erlang term order (sorted), not in insertion order. This shows in `Object.keys`, `for...in`, `JSON.stringify`, and `console.log`.
- `string.length` and string indexes count Unicode code points, not UTF-16 code units. The two differ only for characters outside the Basic Multilingual Plane.
- Integers have arbitrary precision. `2 ** 53 + 1` is exact. Text still converts as JavaScript converts it: `Number(s)`, `parseInt`, `parseFloat`, and `JSON.parse` give the nearest double beyond 2^53.
- An integer has no negative zero, so `0 * -1` is `0` where JavaScript has `-0`. Float operations and `Math.round`, `floor`, `ceil`, and `trunc` keep `-0.0`.
- `console.log` prints an error as `Name: message` and its own fields, without stack frames.
- Buoy has no regular expressions. A string method throws a `TypeError` for a pattern that is not a string.
- `localeCompare` compares code points. `toUpperCase` and `toLowerCase` use the Unicode case mapping without the final-sigma rule.
- `Date` supports `Date.now()`, `new Date()`, `new Date(ms)`, `new Date(isoString)`, `getTime`, `valueOf`, `toISOString`, `toJSON`, and `toString`, all in UTC, for the whole time range of ±8.64e15 ms. Other members throw a `TypeError`. `new Date(text)` reads the date time string format of ECMAScript with the leniencies of V8: a day up to 31 rolls into the next month, `24:00` ends the day, and `t`, `z`, and a space separator are accepted. Text in another format, such as `2020/01/02`, gives an invalid date, where V8 tries more formats.
- A `JSON.parse` error has the V8 message for an unexpected token or for the end of input, such as `Unexpected token ']', "[1,]" is not valid JSON`. V8 has more messages, such as `Expected ':' after property name in JSON at position 5`. For some text, such as `nope`, Buoy reports the end of input where V8 reports an unexpected token. So the message can differ from Node. `JSON.parse` supports no reviver function, and `JSON.stringify` supports no replacer function or array: each throws a `TypeError`. A reviver or replacer that is not callable is ignored, as in JavaScript.
- `Math` functions and `parseInt` beyond 2^53 reproduce V8 on arm64, where the compiler fuses `a * b + c` into one rounding. On x86-64, Node can differ from Buoy in the last bit.
- Arrays have no holes. `Array(n)`, `new Array(n)`, a write past the end, `arr.length = n`, and `delete arr[i]` leave `undefined` items, and `map`, `filter`, `some`, `indexOf`, and the other iteration methods visit them. A list cannot mark a missing item.
- An array is a linked list and a string is a UTF-8 binary, so `push`, `xs[i]`, `s[i]`, and `s.length` take time in proportion to the length. A loop that indexes a long array or string is quadratic. Iterate with `for...of`, `map`, or `reduce`, or split a string with `split("")` once.
- `Object.freeze` returns its argument unchanged. A write to a frozen object succeeds, where strict-mode JavaScript throws a `TypeError`. Values are copies, so freezing protects nothing that Buoy shares.
- Objects have no prototype chain. `Object.create` takes only `null` or `Object.prototype` and gives an empty object; another prototype throws a `TypeError`. `Object.setPrototypeOf` returns its first argument unchanged. `console.log` prints the results of `Object.create(null)` and `Object.groupBy` without `[Object: null prototype]`.
- An iterator is a value too. Only `it.next()` on a variable or a field advances it. `for...of`, a spread, and an iterator helper read the items that are left without using them up.
- A function that is not a module-level declaration has the `name` `""` and prints as `[Function (anonymous)]`. The `length` of every function is `undefined`. An Erlang fun keeps no source name, and every compiled function takes one argument list.
- `this.m` read as a value inside a class is a fun over `This` as it is at that moment, so a later change of the fields does not reach it.
- A method call with a computed name that is not a string literal, such as `m[name](k, v)`, does not write the receiver back, so a mutator that it names changes nothing. Inside a class, `this[name](args)` calls the method through `'C#dispatch'/3` and keeps the change of `this`.
- `m.get(k)` is a place for any `m` (section 6): a write through it, such as `m.get(k).push(v)`, calls `m.set(k, value)`, also on a value that is not a Map.
- A nested function declaration exists from just before the first statement of its block that uses it, and it keeps the values that it captures then (section 12). JavaScript creates it when the block starts and reads the variables when it runs.
- The compiler inlines a module-level `const` with a literal initializer. A function that reads such a const before its declaration runs gets the value, where JavaScript throws a `ReferenceError`. A const with another initializer throws the `ReferenceError` as in JavaScript.

## 4. Calling convention

- Every compiled function and every function value takes one argument: the list of arguments. `buoy_rt:arg(N, Args)` returns argument `N` (1-based) or `undefined`.
- A default parameter compiles to `case buoy_rt:arg(N, Args) of undefined -> Default; V -> V end`. A rest parameter compiles to `buoy_rt:rest(N, Args)`, which returns the arguments from position `N` on.
- A call to a function declared in the same module compiles to a local call `'foo'([A, B])`. A call to a function imported from another Buoy module compiles to a remote call `'buoy@other':'foo'([A, B])`. A call to a library function compiles to a remote call to its Erlang module (section 11).
- A call of any other value compiles to `buoy_rt:call(F, [A, B])`. `call/2` accepts a fun and throws `TypeError: <value> is not a function` for anything else.
- A function used as a value compiles to `fun 'foo'/1` or `fun 'buoy@other':'foo'/1`.

## 6. Mutation and methods

- `let` and reassignment compile to new single-assignment variables (`Count@1`, `Count@2`).
- A place is a local variable, `this`, or a chain of property reads and Map entry reads from one of them: `x`, `x.a.b`, `x[i]`, `this.#items`, `this.#state.users`, `groups.get(k)`. A write through `m.get(k)` reads the entry with `get` and writes it back with `erlang:element(2, buoy_rt:mutate(M, <<"set">>, [K, V]))`, so `groups.get(k)!.push(x)` and `counts.get(k)!.n++` change `groups` and `counts`. An actor ref is not a place, so `ref.add(x)` is an actor call (`buoy_rt:call_method/3`) and not a `Set` mutation. The compiler knows that a value is a ref in two cases. The first is a `const` whose initializer is `spawn(...)` or `supervise(...)` from `buoy`. The second is a variable, a parameter, or a class field whose declared type is `Ref<C>` from `buoy`, alone or in a union with `undefined` and `null`, such as `store: Ref<Store>` or `#peer?: Ref<Peer>`. The type of a field applies to `this.<field>` inside the class that declares it. A library namespace is not a place either.
- `x++` and `++x` compile to `X1 = buoy_rt:sub(X, -1)`, which converts `X` with ToNumber as JavaScript does. When the old value of `x++` is used, it is `T = buoy_rt:to_number(X)` and `X1 = buoy_rt:add(T, 1)`.
- `place = v`, `place += v`, `place++`, and `delete place.k` read the chain, compute the new value, and write it back from the innermost key outward with `buoy_rt:set(Object, Key, Value)` and `buoy_rt:delete(Object, Key)`. Then the compiler rebinds the root variable. Each key expression runs once.
- `r.m(args)`, where `m` is a mutator name and `r` is a place, compiles to `{Result, R1} = buoy_rt:mutate(R, <<"m">>, Args)`. The compiler writes `R1` back to the place, and the expression yields `Result`. The mutator names are `push`, `pop`, `shift`, `unshift`, `splice`, `sort`, `reverse`, `fill`, `copyWithin`, `set`, `add`, `delete`, `clear`, and `next`, which advances an iterator. A string literal key names a method as a static key does, so `xs["push"](1)` is a mutator call.
- The receiver of a mutator may also be a call of a mutator that returns its receiver (`set`, `add`, `sort`, `reverse`, `fill`, `copyWithin`) on a place, or an assignment to a place. The call or the assignment runs first, and then the mutator changes the same place, so `m.set(a, 1).set(b, 2)`, `xs.sort().reverse()`, and `(groups[k] ??= []).push(x)` change `m`, `xs`, and `groups`. Each key expression still runs once.
- `r?.m(args)`, where `m` is a mutator name and `r` is a place, yields `undefined` when the value at the place is `null` or `undefined`. Otherwise it runs the mutator, writes back, and yields the result. The variables that it rebinds come out of a `case` as `{Result, {Vars}}`.
- `Object.assign(place, ...sources)` with the global `Object` is a mutation of the place: `buoy_object:assign/1` returns the merged object, which is the result and the new value of the place. So `Object.assign(this, options)` sets fields of an actor.
- When the right side of a write, or an argument of a mutator, assigns the root variable itself, as in `o.k = (o = other, 5)`, the write changes the old value, which no variable holds any more. The root keeps the value that the right side assigned, as in JavaScript.
- A mutator call or `Object.assign` whose receiver is a value that no variable holds, such as `arr.at(0)!.push(x)` or `(flag ? a : b).push(x)`, is error `BUOY206` when its result is not used, because the change would be lost. The result of a call on a fresh value, such as `const sorted = Object.keys(o).sort()`, is fine.
- Any other method call `r.m(args)` compiles to `buoy_rt:call_method(R, <<"m">>, Args)`, which returns the result only. A computed key that is not a string names a property like any other key, so `handlers[0](x)` calls the item at index 0.
- `this.m` that is not called is a value: `fun(Args) -> erlang:element(1, 'C#m'(This, Args)) end` over the current `This`, so `xs.map(this.label)` and `this.handle.bind(this)` work. A method that rebinds `this` has no such value (`BUOY205`). `this.m?.()` calls the method, because a method always exists. `this[name](args)` with a name that is not a literal compiles to `{Result, This1} = 'C#dispatch'(buoy_rt:to_string(Name), This, Args)` and rebinds `This`. `this.m(a).n(b)`, where every exit of `m` is `return this`, calls `n` on `this` after `m`.
- `this.m(args)` inside a class method compiles to a direct call `'C#m'(This, Args)`. The call returns `{Result, This1}`, and the compiler rebinds `This`. A method that never rebinds `this`, directly or through such a call, leaves `This` as it was, so a call to it compiles to `erlang:element(1, 'C#m'(This, Args))` and does not rebind `This`. A closure may call such a method (section 10, `BUOY205`).
- `call_method/3` and `mutate/3` dispatch on the receiver. A list goes to `buoy_array`, a binary to `buoy_string`, a number to `buoy_number`, `{'$map', _}` to `buoy_map`, `{'$set', _}` to `buoy_set`, `{'$date', _}` to `buoy_date`, `{'$iterator', _, _}` to `buoy_iterator`, and an error map to `buoy_error`, each through the `call/3` or `mutate/3` of that type module (section 11). A ref goes to `buoy_actor:call(Ref, <<"m">>, Args)`, and a `{'$cast', Id}` to `buoy_actor:cast/3`. `{'$namespace', M}` calls the function that `M:'$member'(<<"m">>)` returns. An Effect goes to `buoy_effect:call(<<"m">>, Effect, Args)` (for `pipe`). Another map calls the function in its property `m`. A function and a method value support `call`, `apply`, and `bind`; a method value runs with the first argument of `call` as its receiver, so `Object.prototype.hasOwnProperty.call(o, k)` works. A class supports `captureStackTrace`, which does nothing, because an error records its stack when it is built. Every value has the methods of `Object.prototype`: `hasOwnProperty`, `isPrototypeOf`, `propertyIsEnumerable`, `toLocaleString`, `toString`, and `valueOf`.

## 7. Statements and control flow

Section 12 describes the lowering.

- `if`, `else`, `switch`, conditional expressions, and the logical operators branch with `case`.
- `for`, `while`, `do...while`, `for...of`, and `for...in` compile to named recursive funs. A loop in an actor stays preemptible, because the BEAM scheduler preempts every process after a budget of reductions.
- `throw e` compiles to `erlang:error({'$throw', E})`.
- `try`/`catch`/`finally` compiles to `try ... catch error:Reason:Stack -> E = buoy_rt:caught(Reason, Stack), ... after ... end`. `caught/2` turns `{'$throw', V}` into `V`. It turns an Erlang runtime error (`badarith`, `badarg`, `function_clause`, `{badmatch, _}`, `{case_clause, _}`, `undef`) into an error value named `TypeError`, with two exceptions that JavaScript names otherwise. A `badarg` of `persistent_term:get({Module, <<"x">>})` is a module-level const read before its declaration runs, which is a `ReferenceError`: `Cannot access 'x' before initialization`. An `undef` of a global namespace module is a member that does not exist: `TypeError: Object.fromPairs is not a function`. The `throw` class is reserved for Effect failures (section 13), so a `catch` does not catch them.
- An Erlang exception drops the bindings of the code that raised it, but JavaScript's `catch` and `finally` see the variables as the `try` body left them. So a `try` that rebinds outer variables, and has a `catch` or a `finally` that reads them, records them: `Key = erlang:make_ref()` and `erlang:put(Key, {Vars})` before the `try`, `erlang:put(Key, {Vars})` right after each binding of the body or handler that changes one, such as an assignment, the update of a loop header, or a rebinding earlier in a statement that then throws, `{Vars} = erlang:get(Key)` at the start of the handler and of the `after` block, and `erlang:erase(Key)` in `after`. The key is a fresh ref for each run of the `try`, so recursion and actors cannot mix records.
- A `finally` block that rebinds outer variables cannot be an `after` block, because `after` exports no bindings. Its statements run after the `try`: `Outcome = try {done, try Body catch error:R:S -> Handler end} catch C:R:S -> {raised, C, R, S} end`, then `{Vars} = erlang:get(Key)`, the `finally` statements, and `erlang:raise(C, R, S)` for `{raised, ...}`. A `return`, `break`, or `continue` of the body or handler is rebuilt from the versions that the `finally` statements leave. A `finally` block that itself returns or jumps is error `BUOY206`.
- `async` functions compile like other functions. A BEAM process can block, so a call returns when its result is ready.
- `Promise.all([e1, e2, ...])` compiles each element to a thunk and runs the thunks in parallel processes: `buoy_task:all([fun() -> E1 end, ...])`. `Promise.all(xs.map(f))` compiles to `buoy_task:map(Xs, F)`. `Promise.allSettled`, `Promise.race`, and `Promise.any` compile the same way to `buoy_task:all_settled/1`, `buoy_task:race/1`, and `buoy_task:any/1`, and over `xs.map(f)` to `buoy_task:map_settled(Xs, F)`, `buoy_task:map_race(Xs, F)`, and `buoy_task:map_any(Xs, F)`. Over an array, each worker calls `f` through `buoy_rt:call/2` with the item, the index, and the array, as `map` does, so `Promise.all(xs.map(String))` works. When `f` is an arrow or function literal with at most two parameters and no rest parameter, it cannot read the array, so the compiler passes its parameter count as a third argument, as in `buoy_task:map(Xs, F, 2)`, and each worker gets only its item and its index: no worker copies the array. When `Promise.all` maps with `(x, i) => x.m(args)`, one method call on the first parameter whose arguments are literals or other names, evaluating `f` has no effect besides the call, so the compiler emits `buoy_task:map_call(Xs, F, Params)` instead. For an item that is an actor ref, `map_call` runs `f` in the calling process with the stand-in `{'$defer', Id}`, on which `buoy_rt:call_method/3` returns `{'$deferred', Id, Method, Args}` and makes no call. It sends those calls itself with `buoy_actor:send_call/4`, each to the alias of a monitor of the actor, records each wait in the wait-for graph as a call does, and takes the replies as they come. A batch of more than 256 items splits into one part for each scheduler, and a worker sends each part. A call to an actor that is not running, a call whose process was gone, and an item that is not a ref run in a worker as in `buoy_task:map/3`, so the results, the errors, `CallCycle`, and the waits for a restart are those of `map`. A receiver that is not an array runs its own `map`, whose results are already settled. The results keep the input order. `Promise.any` returns the first value, or throws an `AggregateError` with the errors in input order in `errors`. An empty `Promise.race` never settles: in an actor, the call waits forever, and outside every actor the program prints `Warning: Detected unsettled top-level await` to stderr and halts with status 13, as Node does. When a thunk throws, the call throws the first error in input order, after every other thunk ends. `Promise.resolve(v)` and `Promise.reject(e)` follow the namespace rule (section 11) to `buoy_task:resolve/1`, which returns `v`, and `buoy_task:reject/1`, which throws `e`.

## 8. The `buoy` module

`import { ... } from "buoy"` imports from the Erlang module `buoy`. Each function takes the argument list.

| TypeScript                                                                     | Behavior                                                                                                                                                        |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `spawn(Class, { args?, name?, mailbox?, restart?, maxMemory?, turnTimeout? })` | Starts an actor under `buoy_keeper` and returns its ref. `Class` must be an actor class: an error class throws `TypeError: spawn() needs an actor class`.       |
| `ref.method(...args)`                                                          | A call: sends a request and waits for the reply.                                                                                                                |
| `cast(ref).method(...args)`                                                    | Sends a request without a reply. Returns `true`, or throws `MailboxFull` or `ActorStopped`.                                                                     |
| `stop(ref)`                                                                    | Stops the actor at once, also during a turn. Its waiting callers get `ActorStopped`.                                                                            |
| `inspect()`                                                                    | An array of `{ id, name, class, status, restarts, mailbox, memory }`.                                                                                           |
| `supervise({ strategy?, maxRestarts?, withinMs?, children })`                  | Starts a supervisor with one child for each entry of `children`, and returns an object of refs with the same keys.                                              |
| `child(Class, { args?, restart?, mailbox?, maxMemory?, turnTimeout? })`        | A child specification for `supervise`: `{'$child', Class, Options}`.                                                                                            |
| `schedule(ref, { every } \| { after }, method, ...args)`                       | Casts `method` to the actor once after `after` ms, or every `every` ms. Returns the handle `{'$schedule', Pid}`.                                                |
| `cancelSchedule(handle)`                                                       | Stops the timer of a `schedule` handle, and returns after the timer has stopped, so no cast of the schedule arrives after a message that the caller sends next. |
| `sleep(ms)`                                                                    | Blocks the calling process.                                                                                                                                     |
| `withTimeout(ms, fn)`                                                          | Runs `fn` in a new process. When `ms` passes first, it kills that process and throws `CallTimedOut`.                                                            |
| `self(this)`                                                                   | Inside an actor method: the ref of the actor. Elsewhere it throws `Error`.                                                                                      |

Details of the functions:

- When a constructor throws, `spawn` and `supervise` throw `ActorFailed` for the method `constructor`. `supervise` then stops the children that it started. The actor stays in `inspect()` as `"stopped"`, so a ref that the constructor gave away keeps the label of the actor.
- An actor that a constructor starts, with `spawn` or `supervise`, belongs to the actor of that constructor: it stops when that actor restarts or stops, so a restart does not leave the actors of the previous start running.
- `mailbox.capacity`, `maxRestarts`, and the times in ms take any number without a fraction, such as `64.0` from JSON. A time may exceed 2^32 ms.
- `maxMemory` is the memory limit of the actor: a number of bytes, or a string with a `K`, `M`, `G`, or `T` suffix (powers of 1024), such as `"64M"`, as `BUOY_MAX_MEMORY` takes. Each process of the actor starts with a `max_heap_size` of the limit, with `include_shared_binaries => true`, so the limit counts the heap and the binaries that the process holds. Another value throws `TypeError`, and a limit below the smallest heap of a process throws `RangeError`. At the first garbage collection past the limit, the VM kills the process. Every caller that waits on that process gets `ActorOutOfMemory`, the crash line names that error, and the supervisor restarts the actor as after a crash, within its restart budget. A kill in the first constructor makes `spawn` or `supervise` throw `ActorOutOfMemory`. An actor without `maxMemory` has the limit of every process, which `BUOY_MAX_MEMORY` sets.
- `turnTimeout` is the longest turn of the actor in ms, a positive number without a fraction. A turn that runs longer ends: the timer of the turn fires in `buoy_keeper`, which marks the actor `restarting`, prints the crash line, gives the caller of the turn `ActorTimedOut`, and ends the process with the reason of a crash, so the supervisor restarts the actor with a new `This` within its restart budget, as after a crash. The messages in the mailbox are lost, and their callers get `ActorStopped`. The second slot of the counter of the start names the turn that runs, and the actor and the keeper each swap it atomically, so the keeper ends a turn only while it runs. The limit applies to calls and casts, not to the constructor. Another value throws `TypeError`. An actor without `turnTimeout` has no limit and starts no timer.
- `supervise` starts the children in key order. The key is the name of the child.
- After `stop`, every call or cast throws `ActorStopped`. Inside an actor, `stop` returns before the process ends.
- `inspect` lists the actors in id order. `name` is the `name` option or `undefined`. `status` is `"running"`, `"restarting"`, or `"stopped"`; a restarted actor is `"restarting"` until its constructor ends. `mailbox` is the length of the message queue, and `memory` is the size of the process in bytes. The table keeps the 1000 stopped actors with the highest ids and forgets older ones, so a program that starts and stops actors forever keeps bounded memory. A call through a ref of a forgotten actor throws `ActorStopped` with the label `actor #<id>`.
- The timer of `schedule` is a process that monitors its owner: the actor whose turn or constructor calls `schedule`, also from a `buoy_task` worker, or else the top-level code. It ends with its owner, and when the actor stops. A full mailbox skips one cast, whatever the overflow of the mailbox, so a timer never waits.

Actor semantics:

- `buoy_main` starts the runtime with `buoy_app:start(normal, [])`, which needs no `.app` file. `application:ensure_all_started(buoy)` also works when `buoy.app` is on the code path.
- An actor is a process (`buoy_actor`) that runs a receive loop, not a `gen_server`, whose state holds the class and `This`, kept beside the state so a turn does not copy it. A call is the message `{'$call', Alias, Method, Args, Chain}`, where `Alias` is the alias of the monitor of the caller (`{alias, reply_demonitor}`), and the actor replies `{Alias, {ok, Value}}` or `{Alias, {throw, Error}}`. A cast is `{'$cast', Method, Args}`, and a cast that waits for room is `{'$room', Alias, Method, Args}`, which the actor answers `{Alias, true}` when it takes it. The loop drops any other message. Its process runs `'C#new'/1` before it takes a request: in `init_tree/2` for a child of `supervise`, whose group supervisor calls `start_link/1`, and in `init_alone/2` for an actor that `spawn` starts, except that a pure constructor (section 9) runs in the spawner, and its process starts in `init_ready/4`. Then the first process of an actor waits for its first request hibernated, so an actor that takes no request holds only its live data; a restarted process does not hibernate, since the callers that waited for the restart call it at once. The process keeps its message queue off its heap (`{message_queue_data, off_heap}`), so a full mailbox does not grow the heap that each garbage collection copies. A call runs `'C#dispatch'/3` and replies with the result. The top-level code also keeps its message queue off its heap, so the replies of many workers to it do not contend for one lock.
- A turn is one call or one cast. The process handles one message at a time, so turns never interleave.
- Identity: an id is a positive integer. The ETS table `buoy_actors` maps an id to the mode of the actor, its last pid, the count of its starts, whether it is stopped, and the facts that stay fixed for its life: the class, the module, the constructor arguments, the name, the mailbox policy, the restart type, and the supervisor. The mode is `{running, Pid, Counter, Mailbox}` once the constructor of process `Pid` has finished, `{starting, Pid, Counter, Mailbox}` while it runs, `restarting` while no process serves the actor, or `stopped`. A call or a cast reads only the mode. A restart keeps the id, so a ref stays valid after a restart.
- A thrown error in a turn: the actor replies `ActorFailed` to the caller and exits. `ActorFailed` is an error value with `_tag` `"ActorFailed"`, the actor label in `actor`, the method in `method`, and the original error as `cause`. The supervisor restarts the actor with a new `This` from `'C#new'/1` and the original arguments. Messages in the mailbox of the failed process are lost, and their callers get `ActorStopped`. This is the BEAM model. A call that starts after its caller got `ActorFailed` waits for the restart. A caller that waits for a restart or for a constructor records itself in the ETS table `buoy_watchers` and blocks until the next change of the mode, which each change announces with a message, or until the supervisor of the actor ends. A new process whose constructor runs wakes only the casts that wait for a process, since a call waits for the constructor. It never polls.
- A method that returns an Effect: the actor runs the Effect in the same turn. A success replies the value. A typed failure replies the failure, the caller throws it, and the actor keeps its state. A defect crashes the actor. A typed failure in a cast has no caller, so the actor drops it.
- Mailbox (`mailbox: { capacity?: number, overflow?: "backpressure" | "reject" }`, default capacity 1024 with `backpressure`): the counter in the mode of the actor, an `atomics` array of one start, counts the requests that the actor has not taken yet. A sender adds one to the count before it sends, atomically with `atomics:add_get/3`, and the actor takes one off when it takes a request, so concurrent senders cannot pass the capacity together. The count belongs to one start of the actor: a new process gets a new counter at zero, because the messages of a dead process are lost. With `reject`, a full mailbox throws `MailboxFull` to a call or a cast. With `backpressure`, a cast to a full mailbox becomes a call, so the sender waits until the actor takes the message. A call always waits. So the mailbox holds at most the capacity plus one message for each blocked sender. A cast to an actor that waits on the sender, as a member of its call chain or through the wait-for graph, goes in at once, because that actor could never take it otherwise. A blocked cast throws `ActorStopped` when the actor stops, and counts as sent when a crash loses it.
- Call cycles: a call carries the chain of actor ids that wait on it. A call to an actor in its own chain throws `CallCycle` instead of a deadlock. A call or a blocked cast from inside an actor also records its wait in the ETS table `buoy_waits`, the wait-for graph, before it looks for a path from the target back to its chain. So of two turns that call each other at once, at least one sees the cycle, and its call throws `CallCycle`. A constructor never throws `CallCycle` for a path in the graph: a call to an actor waits until the constructor of that actor ends, and looks for the cycle while it waits, so the call that waits on a restart throws `CallCycle` and the restart completes. Each wait that a constructor records wakes the callers that wait on that constructor, so they look for the cycle again. The processes of `buoy_task`, `withTimeout`, and the Effect workers (section 13) inherit the chain of their caller. A `Promise.race` that has returned ends the chain of its losers, so a loser that keeps running calls as top-level code does.
- Supervision maps to OTP. `"one-for-one"`, `"one-for-all"`, and `"rest-for-one"` map to the OTP strategies of the same names. `maxRestarts` and `withinMs` (default 3 in 5000) map to `intensity` and `period`. OTP counts `period` in whole seconds, so `withinMs` rounds up. The restart types are `"permanent"`, `"transient"` (the default), and `"temporary"`. A crash exits with the reason `{shutdown, {crashed, Id}}`, and an actor never exits normally, so `"transient"` maps to the OTP type `permanent`. `buoy_root_sup` owns the actor tables and supervises `buoy_keeper` and `buoy_groups`. An actor that `spawn` starts is one process, linked to `buoy_keeper`, which restarts it in a new process after a crash, with a budget for each actor: 3 restarts within 5 seconds, counted as an OTP supervisor counts `intensity` and `period`. So a crashing actor cannot use up the restart budget of another actor, and a slow constructor never blocks the keeper. Each `supervise` call starts an OTP group supervisor under `buoy_groups`. A supervisor that uses up its budget stops its actors: the keeper marks them `"stopped"`, also when a group ends or a temporary child of a group ends, and later calls and casts throw `ActorStopped`. A group supervisor ends with its last actor: when that actor stops, or when a temporary actor crashes. `stop` marks the actor stopped and then ends its last process with the exit signal `{shutdown, stopped}`, or kills the group of the actor, so a constructor that runs never blocks other spawns. A restart that starts after the mark sees it and ends at once. A group ends a child with the exit signal `shutdown` (a shutdown time of 5000 ms), so an actor process that ends with the reason `killed`, without the mark of `stop`, passed its memory limit. The keeper prints the crash line of such an actor and restarts it when `spawn` started it. It watches a child of a group that has `maxMemory` and prints its crash line, and the group restarts the child.
- A crash prints one line to stderr: `buoy: <class> <name or #id> crashed: <name>: <message>`. The text after `crashed: ` is `String(error)`, so an empty message prints only the name. The crashed actor sends the line to the `standard_error` server before it replies to its caller and does not wait for the write, so the line comes before any later write of that caller to stderr, and `buoy_main` waits for the server before the VM halts. The runtime drops the OTP supervisor reports of its own supervisors.

The runtime errors are error values (section 3) with the error name in `name` and `_tag`. `<actor>` is the label of the actor, `<class> <name>` or `<class> #<id>`. `<cause>` is `String(cause)`.

| Error              | Own fields                 | `message`                                                                                             |
| ------------------ | -------------------------- | ----------------------------------------------------------------------------------------------------- |
| `ActorFailed`      | `actor`, `method`, `cause` | `<actor> failed in <method>: <cause>`                                                                 |
| `ActorStopped`     | `actor`                    | `<actor> is stopped`                                                                                  |
| `MailboxFull`      | `actor`                    | `<actor> has a full mailbox`                                                                          |
| `CallCycle`        | `actor`                    | `<actor> is busy with a call that waits on this call. Use cast() or pass the data in the first call.` |
| `CallTimedOut`     | `ms`                       | `the call did not finish within <ms> ms`                                                              |
| `ActorOutOfMemory` | `actor`, `limit`           | `<actor> used more than its memory limit of <limit> bytes`                                            |
| `ActorTimedOut`    | `actor`, `method`, `ms`    | `<actor> did not finish <method> within <ms> ms`                                                      |

## 9. Classes

A class without `extends` is an actor class. `new` on an actor class is error `BUOY203`. Use `spawn`.

- `'C#new'(Args) -> This` binds the constructor parameters, runs the field initializers in order, runs the constructor body, and returns `This`. `This` is a map from field key to value. A public field `x` has the key `<<"x">>`. A private field `#x` has the atom key `'#x'`, which JSON and object literals cannot make: `this.#x` is `maps:get('#x', This, undefined)`, and a write is `maps:put/3`. The runtime lists only binary keys as properties, so `JSON.stringify(this)`, `Object.keys(this)`, a spread, `in`, and `console.log` do not show a private field. `this.constructor` in an actor class compiles to the class value `{'$class', Module, <<"C">>}`.
- `'C#pure'() -> true` exists when `'C#new'/1` calls only `buoy_rt:arg/2`, `buoy_rt:rest/2`, `maps:put/3`, and `maps:get/3`, and binds only fresh variables, so it has no effect and cannot throw. `spawn` then runs `'C#new'/1` in the calling process, starts the actor process with its `This`, and writes its row as `running`, without a wait for the process. A restart runs `'C#new'/1` in the new process, as for any class. An actor with `maxMemory` always runs its constructor in its own process.
- `'C#dispatch'(Method :: binary(), This, Args) -> {Result, This1}` has one clause for each public method. Another name throws `TypeError: <class>.<method> is not a function`.
- `'C#m'(This, Args) -> {Result, This1}` exists for each method, private methods included.

A class with `extends Error`, `extends Data.TaggedError("Tag")`, or `extends Data.Error` is an error class. A base resolves as any name does: `Error` is the global class only when no declaration of the module shadows it, and `Data` must be the import of `Data` from "effect". `new E(args)` compiles to `'E#new'(Args)`, which builds an error value with `buoy_error:new([{'$class', Module, <<"E">>}, {'$class', buoy_error, <<"Base">>}], Message, Fields)`: the classes of the error, with `Base` the global error class that `E` extends (`Error` for `Data.TaggedError` and `Data.Error`), `name` set to the class name, and `_tag` for a tagged error. `instanceof` tests the classes, so renaming an error keeps its class, and two classes with one name in two modules stay apart. `this.constructor` in the constructor is the class, and `Object.setPrototypeOf(this, E.prototype)` changes nothing. Without a constructor, `Message` is the first argument as a string (`<<>>` for `undefined`) for `extends Error`, and the `message` field of the first argument for `Data.TaggedError` and `Data.Error`, whose first argument is also `Fields`. An error class may declare `readonly` fields without initializers, which are types only, and fields with initializers, which `'E#new'/1` sets after the error is built. It may also declare a constructor whose first statement is `super(...)`. `super(args)` builds the error from `args` as above, and the rest of the constructor runs with `this` bound to the error, so `this.name = "E"` and `this.field = value` set fields. With a global base, the second argument of `super(message, options)`, or of `new E(message, options)` without a constructor, gives the field `cause` when `options` has the key `cause`, as the global error classes do. The parameter properties of the constructor, such as `constructor(public status: number)`, set their fields after the field initializers. An error class declares no methods.

The constructor of any class is the one with a body: the overload signatures before it are types.

The global error classes `Error`, `TypeError`, `RangeError`, and `SyntaxError` are bases of an error class too. `extends` of any other class is error `BUOY206`.

## 12. Lowering control flow

The compiler keeps a map from each oxc `SymbolId` to the Erlang name of its current version. An assignment creates a new version. A construct that rebinds variables declared outside it returns their new versions, and the code after the construct binds them.

A statement completes normally, or it completes abruptly through `return`, `break`, or `continue`. A `throw` is an Erlang exception, so it needs no completion. Each lowered block knows its frame:

- In the top-level sequence of a function body, `return e` becomes the final expression `E`, and falling off the end yields `undefined`.
- An `if` or `switch` whose branches all complete normally is an expression that yields the tuple of the variables it rebinds: `{X@2, Y@1} = case ... end`.
- An `if` or `switch` with an abrupt branch yields a tagged completion: `{next, {X@2, Y@1}}`, `{return, V}`, `{break, State}`, or `{continue, State}`. The compiler lowers the code after the construct once, inside the `{next, ...}` clause of a `case` on the completion. The other clauses forward the completion to the enclosing frame. In a function frame, `{return, V}` yields `V`. `State` is the tuple of the variables of the target: the state of a loop, or the variables that a `switch` rebinds.
- Two shapes need no completion. An `if` with an abrupt branch and at most one branch that can reach its end lowers the code after it once, inside that branch, and each jump lowers in place: `case C of true -> V; false -> Rest end` for `if (c) return v; rest`. A `switch` with a `default` whose every case ends in a jump other than `break` is a plain `case` whose clauses lower in place.
- A loop is a named fun over a state tuple of the variables that the loop rebinds: `Loop = fun Loop({I, Sum}) -> ... end`. Falling through and `continue` run the update expression and call `Loop` with the new state. `break` yields `{break, State}`. `return e` yields `{return, V}`. After the loop, a `case` binds the state from `{break, State}` and forwards `{return, V}`. A loop without `return` binds the state directly: `{break, {I@9, Sum@4}} = Loop({I@1, Sum@1})`. The fun of `for...of` and `for...in` also takes the remaining items: `Loop([X | Rest], State)` and `Loop([], State) -> {break, State}`, over `buoy_rt:to_list/1` or `buoy_rt:keys/1` of the right side.
- A `try` block that rebinds outer variables yields the tuple of the rebound variables from both the body and the handler. The handler starts from the recorded versions of section 7.
- A conditional expression or a logical operator whose right side rebinds variables yields `{Value, {Vars}}`, and so does a logical assignment such as `cache ??= (hits++, "filled")`. An expression statement `a && f()`, `a || f()`, or `c ? f() : g()` lowers as an `if`.
- A `switch` tests its cases in source order and takes `default` only when no case matches. The tests that share a body with `default` run at their place in that order.
- The function declarations of a block are created just before the first statement of the block that uses them, so that they capture the latest values, and a function can be called before its declaration. A function that a used function calls is created no later. Functions that call each other are created together as one named fun that returns all of them: `Group = fun Group() -> {fun(Args) -> {F, G} = Group(), ... end, ...} end`, then `{F, G} = Group()`. A function that nothing uses is created at its declaration. A function used before a variable that it reads is declared is `BUOY205`.

A pre-pass over the subtree of a construct finds the variables it rebinds. They are the targets of every write reference to a symbol declared outside the subtree, plus the root variable of every place that a mutation or a mutator call writes (section 6). `this` counts as the variable `This`.

An Effect is `{'$effect', Thunk}` (section 3). Running it calls `Thunk()`, which returns `{ok, Value}` or `{error, Failure}`. A defect, from `Effect.die` or from an exception in a function such as the one that `Effect.sync` or `Effect.map` takes, is a JavaScript exception, so it passes every combinator that does not handle it. An error value is an Effect too, which fails with itself, as a `Data.TaggedError` instance does in Effect. `Effect.result` gives the object `{ _tag: "Success", success }` or `{ _tag: "Failure", failure }`. A DurationInput is a number of milliseconds, a string such as `"100 millis"` or `"1.5 seconds"`, or a duration.

A generator function is the body of an Effect. A call of it returns `buoy_effect:generator(fun() -> Body end)`, an Effect whose thunk binds the parameters and runs the statements. The `return` value is the success value. So `Effect.gen(body)` calls `body`, and the function of `Effect.fn` calls `body` with its arguments, each time the Effect runs. In the body, `yield* e` compiles to `buoy_effect:bind(E)`, which runs `e` and returns its value. A failure ends the body with `erlang:throw({'$fail', Failure})`, and a defect with `erlang:throw({'$die', Defect})`. The thunk of `generator/1` turns the first into `{error, Failure}` and raises the second again as a JavaScript exception. A `catch` clause lowers to the `error` class only (section 7). In a generator body, a `finally` block lowers to the outcome form of section 7, with a first clause that rethrows the `throw` class. So no `catch` or `finally` of the body runs after a failed `yield*`, as in Effect, which abandons the generator. A JavaScript `throw` in the body is a defect, and the `catch` and `finally` of the body see it.

The compiler rejects `yield` without `*`, a `yield*` in a function nested in a generator, an `async` generator, and a generator method with `BUOY206`. oxc reports a nested `yield*` as the use of a reserved word, and the compiler reports it as `BUOY206`. A generator function is a closure, so the capture rule of `BUOY205` applies to it, and `this` in it is `BUOY206`.

A worker of `all`, `forEach`, `zip`, `race`, and `timeout` adopts the actor context of its caller and is linked to it, as the workers of `buoy_task` are. An actor method that returns an Effect runs it in the same turn (section 8).

Known differences from Effect. Each one is a documented limitation:

- A killed worker runs no finalizers: an `ensuring` finalizer inside work that a timeout, a race, or a failed sibling interrupts does not run, where Effect runs it.
- `runSync` and `runPromise` block until the Effect ends. `runSync` also runs an asynchronous Effect, where Effect throws, and `runPromise` without `await` ends before the next statement runs.
- `console.log` prints an Effect as `[Effect]`, a schedule as `[Schedule]`, and a Result with its fields, `{ _tag: 'Success', success: 1 }`, where Effect prints `{ _id: 'Result', _tag: 'Success', value: 1 }`. A `Data.TaggedError` instance prints as an error (section 3), where Effect prints only its fields, and `String()` of a SchemaError is `SchemaError: <message>`, where Effect gives `SchemaError(<message>)`.
- `Effect.all` over a record runs the Effects in key order, and `Schema.Struct` checks and returns its fields in key order, because object keys are sorted (section 3). With several invalid fields, the issue in the message can differ from the one Effect reports. Decoding stops at the first issue, and a SchemaError has no `issue` field.
- `Schedule.fixed` waits the whole interval after each failure, as `spaced` does. The function of `Effect.promise` and `Effect.tryPromise` gets no AbortSignal. `Effect.gen({ self }, body)` ignores `self`.

The rules:

- Endpoint. `@ai-sdk/openai` 4.x sends `openai(model)` and `openai.languageModel(model)` to the Responses API. Buoy sends every model to the Chat Completions API, `POST <baseURL>/chat/completions`, as `openai.chat(model)` does, because every OpenAI-compatible server serves it. The equivalence programs use `openai.chat`. A model that only the Responses API serves fails with an `APICallError`.
- Configuration. The provider reads `baseURL`, or else `OPENAI_BASE_URL`, when it is made, and drops one trailing slash. The default is `https://api.openai.com/v1`. It reads `apiKey`, or else `OPENAI_API_KEY`, when it sends a request, as the package does, so a missing key throws `AI_LoadAPIKeyError` from `generateText`.
- A model is `#{<<"specificationVersion">> => <<"v4">>, <<"provider">> => <<"openai.chat">>, <<"modelId">> => Id, '$generate' => Fun}`. The `name` option of `createOpenAI` replaces `openai` in the provider. `generateText` calls the fun under the atom key, so a model of another provider, such as a gateway string, throws a `TypeError`.
- Requests. The provider sends the body of the package: `model`, `messages`, `tools`, `tool_choice`, and the settings. A reasoning model (the o series, and GPT 5 and later except the chat variants without a minor version) gets the system prompt as a `developer` message, sends `max_completion_tokens`, and drops the sampling settings with a warning in `warnings`. User messages hold text only: an image or a file part throws a `TypeError`.
- HTTP. The provider calls OTP `httpc`. It starts `inets` on the first request, and `ssl` for an `https` URL, where it verifies the server with `httpc:ssl_verify_host_options(true)`. Before them it adds `inet_db`, the resolver configuration that the minimal kernel leaves out (section 1), to the kernel supervisor. A program without AI calls does not start them. `buoy_json` encodes the body and decodes the response, so the values follow `JSON.stringify` and `JSON.parse`.
- Steps. Each step calls the model, parses each tool call, and runs the `execute` functions of the step in parallel processes (`buoy_task:all/1`), as `Promise.all` runs them. `execute` gets the input and `{ toolCallId, messages }`. The next step starts while every tool call of the step has an output and no stop condition holds. The default stop condition is `stepCountIs(1)`. A call of an unknown tool, input that is not JSON, and an `execute` that throws give a `tool-error` output, and the model gets the error message, as in `ai`. A `toolChoice` of `"required"` or of one tool throws `AI_ToolChoiceViolationError` when the model calls no matching tool.
- Errors. An AI SDK error is an error value (section 3) whose classes are `{'$class', buoy_ai, <<"APICallError">>}` and `Error`, and whose name is `AI_APICallError`, with the fields of the package. A response with a status other than 2xx, a response that is not JSON, and a failed connection throw `AI_APICallError` with `url`, `requestBodyValues`, `statusCode`, `responseHeaders`, `responseBody`, `isRetryable`, and `data`. The message is the `error.message` of an OpenAI error body, or else the status text. `generateText` retries a retryable `APICallError` (status 408, 409, 429, or 500 and above, or a failed connection) `maxRetries` times, default 2, after 2 s and then 4 s, or after the delay of a `retry-after-ms` or `retry-after` header when that delay is below 60 s or below the backoff. Then it throws `AI_RetryError` with `reason`, `errors`, and `lastError`. A bad prompt throws `AI_InvalidPromptError`, and a bad `maxRetries` throws `AI_InvalidArgumentError`.
- The result and each step hold the values of the getters of `ai` as fields: `text`, `content`, `toolCalls`, `toolResults`, `finishReason`, `usage`, `response`, `steps`, and the others.

Known differences from the packages. Each one is a documented limitation:

- `openai(model)` and `openai.languageModel(model)` use Chat Completions, as described above.
- `result.output` is `undefined` where `ai` throws `NoOutputGeneratedError`, and `Object.keys` of a result or a step lists the fields that `ai` computes in getters. A step has no `performance` field.
- The error classes, such as `APICallError`, are not exports. Test `error.name`, such as `"AI_APICallError"`.
- Tools go to the model in key order (section 3), where Node keeps insertion order. The list of the tools in a `NoSuchToolError` message is sorted the same way.
- Buoy does not support Zod or other Standard Schema input schemas, `toModelOutput`, a tool that streams its output, `system` messages in `messages`, the `on...` callbacks, `prepareStep`, `activeTools`, `abortSignal`, `timeout`, `providerOptions`, or `output`. A `retry-after` header that holds a date counts as absent. The `user-agent` header names the runtime `buoy`.

The fake server, `runtime/test/buoy_fake_openai.erl`, serves the tests. `erl -noshell -pa <dir> -eval 'buoy_fake_openai:main()' -extra stdin` prints its port on the first line of stdout and serves until its stdin closes, which `crates/buoy-cli/tests/ai.rs` uses. With `-extra <os pid>`, which `scripts/freeze-expectations.sh` uses, it serves until that process ends. EUnit starts it in the test VM with `start/0`. The model name picks the answer: `fake-500` gets HTTP 500, a name that ends in `echo` gets the request path, body, and headers back as text, `fake-length` gets the finish reason `length`, and another name gets a scripted answer. A prompt that holds `CALLS <json>` scripts the tool calls of each step, and a prompt that holds `JSON <json>` gets that JSON as its text. The key `sk-fake-key` is the only valid one, and another key gets HTTP 401. The server also serves the OpenAI Responses API (`POST <baseURL>/responses`) and the Anthropic Messages API (`POST <ANTHROPIC_BASE_URL>/v1/messages`, with the key in `x-api-key`) for the scenarios of [testing.md](testing.md) section 5.8, and a request with `"stream": true` to any of the three APIs gets its answer as server-sent events.

## 17. Reference semantics

`--semantics reference` selects the JavaScript engine of [ADR 0003](../adr/0003-run-typescript-on-beam.md). Each actor is one realm: one BEAM process with a heap of objects in its process dictionary, a promise job queue, and the intrinsics of section 17.6. Sections 2 to 16 describe `--semantics value`. This section describes `--semantics reference`, and it replaces them when Phase 3 of the ADR ends.

### 17.1 Values

Every JavaScript value has exactly one Erlang term. So `=:=` decides SameValue, and any value can be a key of an Erlang map.

| JavaScript  | Erlang term                                                                                                                                                                                                                               |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `undefined` | `undefined`                                                                                                                                                                                                                               |
| `null`      | `null`                                                                                                                                                                                                                                    |
| boolean     | `true`, `false`                                                                                                                                                                                                                           |
| number      | an integer `I` with `abs(I) =< 2^53`, for every integral value in that range; a float for any other finite value, and `-0.0` for -0; the atoms `'NaN'`, `'Infinity'`, and `'-Infinity'`                                                   |
| string      | a binary when every UTF-16 code unit is at most `16#FF`, one byte for each unit; else `{'$u16', Binary}`, two bytes for each unit, big-endian                                                                                             |
| BigInt      | `{'$bigint', Integer}`                                                                                                                                                                                                                    |
| symbol      | `{'$sym', Tag, Description}`: `Tag` is a unique integer for `Symbol()`, `registered` for `Symbol.for(Key)`, whose description is the key, or the atom of a well-known symbol, such as `iterator`                                          |
| object      | `{'$o', Id}`: `Id` is a positive integer, the atom of an intrinsic, such as `'Object.prototype'`, or `{N, Atom}` for that intrinsic of the realm N > 0 of the process (section 17.2)                                                      |
| function    | `{'$f', Id, Fun}`, with `Fun` of arity 2, `fun(This, Args)`. `Id` is an integer, `{builtin, Name}` for a builtin, `{N, {builtin, Name}}` for that builtin of the realm N, or `{fn, Module, Name}` for a module-level function declaration |
| actor ref   | `{'$actor', Pid}`                                                                                                                                                                                                                         |

A heap cell, `{'$c', Id}`, holds a variable that a closure writes. It is never a JavaScript value.

**Numbers.** JavaScript numbers are doubles. JSC keeps a double that is an exact int32 as an int32, and only other values as doubles (`JSValue::JSValue(double)` in WebKit's `Source/JavaScriptCore/runtime/JSCJSValueInlines.h`). V8 keeps small integers as Smis. Buoy follows the same rule with a wider range. A BEAM small integer is an immediate term of 60 bits, and a float is a boxed term on the process heap, so integers are the fast path. Every integer with `abs(I) =< 2^53` is exactly a double, so the integer form never changes a result. BEAM floats cannot hold NaN or an infinity, so those values are atoms.

`buoy_ref_number:canonical/1` turns any Erlang number into this form, and every operation returns it:

- An integer result outside the range becomes the nearest double. BEAM converts a big integer to a correctly rounded double, so `2^53 + 1` is `2^53`. A result past the largest double is an infinity.
- A float result that is integral and in the range becomes an integer. So `0.5 + 0.5` is `1`.
- A product, quotient, or remainder that is zero has the sign that IEEE 754 gives it, such as `0 * -5` and `-5 % 5`, which are `-0.0`.
- A float operation that overflows raises `badarith` in Erlang, and the result is the infinity of its sign.
- The bitwise operators convert with ToInt32 or ToUint32 and return integers.

`===` on two numbers is `==` in Erlang, so `0 === -0` holds, and `'NaN'` is never equal to itself. SameValueZero, the key equality of `Map`, `Set`, and `includes`, maps `-0.0` to `0` and then compares terms. `buoy_ref_number:to_string/1` prints the shortest digits that read back to the same double, as `Number.prototype.toString` does.

**Strings.** A JavaScript string is a sequence of UTF-16 code units, and a code unit can be a lone surrogate. JSC stores a string in an 8-bit (Latin-1) or a 16-bit buffer (`is8Bit()` in WebKit's `Source/WTF/wtf/text/StringImpl.h`), and Bun uses these strings. V8 has one-byte and two-byte strings. Buoy uses the same two forms, and a string with every unit at most `16#FF` always takes the one-byte form:

- `length` is `byte_size/1`, or half of it, and an index is a binary match, so both take constant time.
- A lone surrogate is a unit like any other.
- ASCII text has the same bytes in Latin-1 and in UTF-8. So the binary literals of the runtime, such as `<<"length">>`, are strings of the engine as they are.
- Two strings are equal exactly when their terms are equal.

Concatenation appends binaries; BEAM appends in place when the left binary is the newest one, so the engine has no ropes. Slicing returns a sub-binary, and the slice of a two-byte string becomes one-byte when it can. The module `buoy_ref_string` holds these operations.

Text crosses the boundary of the engine in two functions. `buoy_ref_string:from_utf8/1` reads UTF-8 and replaces each byte that does not decode with U+FFFD. `buoy_ref_string:to_utf8/1` writes UTF-8 and replaces each lone surrogate with U+FFFD, as Node does when it writes to a stream. Console output, JSON text, the dates and number text of the value core, and the host use these functions. `JSON.stringify` writes a lone surrogate as a `\uXXXX` escape, so its output holds no lone surrogate. The compiler writes each string literal in the engine form (`Expr::JsString`). It reads a lone surrogate from the escape that oxc uses for it.

**BigInt.** An Erlang integer is a number in this form, so a BigInt needs a tag of its own. `{'$bigint', I}` holds the value as an Erlang integer of any size, and `buoy_ref_bigint` holds its operations. Erlang's bitwise operators treat integers as infinite two's complement, as BigInt does. A result past 2^30 bits is a `RangeError`, as in V8. The compiler writes a BigInt literal as this tuple.

**Primitive wrappers.** `new Number(1)`, `Object("s")`, and the other wrappers are objects of the classes `number`, `string`, `boolean`, `bigint`, and `symbol`, with the primitive in their slots. `buoy_ref:to_object/1` makes them, and each prototype method unwraps them (thisNumberValue and the others). A String object holds its code units as read-only index properties and its `length`. A property read on a primitive looks up the prototype with the primitive as the receiver of a getter.

### 17.2 Objects

The heap entry of an object is the record `{Class, Proto, Props, Keys, Attrs, Slots}` under its integer id in the process dictionary:

- `Class` is the kind of the object: `object`, `array`, `function`, `error`, `map`, `set`, `promise`, `generator`, `list_iterator`, `array_iterator`, `map_iterator`, `set_iterator`, `string_iterator`, `date`, `regexp`, `regexp_string_iterator`, `arguments`, `raw_json`, `proxy`, `namespace`, `deferred_namespace`, `weakmap`, `weakset`, `weak_ref`, `finalization_registry`, `date_time_format`, a primitive wrapper (`number`, `string`, `boolean`, `bigint`, `symbol`), or a class of binary data (`array_buffer`, `shared_array_buffer`, `typed_array`, `data_view`).
- `Proto` is `null` or an object or function value.
- `Props` maps each key to a value, or to `{'$accessor', Get, Set}`.
- `Keys` holds the string and symbol keys, newest first.
- `Attrs` maps a key to its attribute bits (writable 1, enumerable 2, configurable 4) when they are not all set, and holds `'$frozen'` or `'$noext'` for a frozen or a non-extensible object.
- `Slots` holds the internal slots of the class.

An intrinsic is a static record in `persistent_term` that every realm reads. A realm copies the record into its heap when it first writes to the intrinsic. The static record `{lazy, Module}` stands for an intrinsic that each realm builds on its first read: `buoy_heap` calls `Module:load(Id)`, which puts the record in the heap of the realm and returns it. `Temporal` is such an intrinsic (section 17.3). The collector, `buoy_heap:gc/1`, marks and sweeps between jobs, when the stack is empty.

**More realms in one process.** `buoy_ref_realm:create/0` makes another realm in the process, as `$262.createRealm()` of test262 needs, and returns its global object. The N-th such realm names each intrinsic `{N, Id}`: `{'$o', {N, 'Array.prototype'}}`, `{'$f', {N, {builtin, Name}}, Fun}`, and `{'$f', {N, 'Function.prototype'}, Fun}`. On first use, the realm copies the record of realm 0 into its heap with every intrinsic in it replaced by its twin of realm N (`buoy_ref_realm:localize/2`). The current realm is the pdict key `'$buoy_realm'`, absent for realm 0. Each builtin of the realm N, each construct fun in its records, and each function that code of the realm N makes (`buoy_heap:function/4`, which also stores `realm => N` in its slots) sets the key to N while it runs. The macros `?OBJECT_PROTO`, `?FUNCTION_PROTO`, and `?ITERATOR_PROTO`, `buoy_heap:intrinsic/1`, error objects, primitive prototypes, and global names use the current realm. GetFunctionRealm is `buoy_ref_realm:function_realm/1`: a proxy and a bound function take the realm of their target, and `buoy_ref_realm:proto_for/2` takes the default prototype from the realm of `new.target`. Code of realm 0 never sets the key, so it pays one pdict read where it reads an intrinsic. A function of realm 0 that a builtin of another realm calls back runs in that realm, except a Proxy trap (`buoy_ref_realm:callee/1`). `Symbol.for` and the well-known symbols are terms, so every realm shares them.

`buoy_heap` implements the internal methods of ECMA-262 §10.1 over these records: `get/3` ([[Get]] with a receiver), `set/4` ([[Set]]), `get_own/2`, `define_own_property/3`, `has/2`, `delete_property/2`, `own_keys/1`, `prototype_of/1`, `set_prototype/2`, `is_extensible/1`, and `prevent_extensions/1`. The functions that return a boolean report a failure. `set/3`, `delete/2`, and `define/3` throw a TypeError instead, as strict code does, and `sloppy_set/3` ignores a failure. `define_own_property/3` validates the descriptor as ValidateAndApplyPropertyDescriptor does, and an array's `length` follows ArraySetLength. An own property is `{data, Value, Bits}` or `{accessor, Get, Set, Bits}`.

- A proxy has the class `proxy` and the slots `{Target, Handler}`, or `{revoked, IsConstructor}` after a revoke. A proxy of a callable target is a function value. Each internal method of a proxy record goes to `buoy_ref_proxy`, which runs the trap and its invariant checks.
- A mapped arguments object, of a sloppy function with simple parameters, has the class `arguments` and slots that map each index to the heap cell of its parameter. An unmapped one has the slots `none`.
- `weakmap` and `weakset` hold their entries in a map in their slots, `weak_ref` its target, and `finalization_registry` `{Cleanup, [{Target, Held, Token}]}`. The collector does not mark through these keys and targets. It marks the value of a WeakMap entry while its key is live, until nothing new becomes live (ephemerons), then drops the entries of dead keys, empties each WeakRef whose target died, and queues the cleanup callback of each registry cell whose target died as a job.

V8 and JSC share one hidden class (a Map in V8, a Structure in JSC) among objects with the same keys, and inline caches remember where a key is. Buoy keeps a map for each object. Shapes and inline caches are Phase 5 of ADR 0003.

### 17.3 Arrays

An array has the class `array` and the slots `{Length, Elements}`. `Elements` maps each index to its value or to `{'$accessor', Get, Set}`, and a missing index is a hole; an array literal with elisions makes holes. `length` is in the slots, not in `Props`, and `Attrs` holds its bits only after a program defines it: it is writable, not enumerable, and not configurable, and a write converts the value with ToUint32 (ArraySetLength). `push` reads and writes the record once for any number of items while neither intrinsic prototype holds an index, so no setter on the chain can see the new elements. The methods of `Array.prototype` follow their algorithms over any object, with HasProperty for holes and ArraySpeciesCreate for their results. `Array.prototype` is itself an array. V8 and JSC keep packed arrays of small integers, doubles, or values in a contiguous store, and holey or sparse arrays in other stores. A contiguous store for dense arrays is future work.

**Map and Set.** The slots of a Map or a Set are `{Index, Order}`. `Index` maps each key, with -0 as 0, to `{Seq, Value}` for a Map and to `Seq` for a Set, where `Seq` counts insertions. `Order` is `{Next, Tree}`, a `gb_trees` from each live `Seq` to its key, so an iterator or `forEach` that remembers its last `Seq` sees the entries that a callback adds and skips the ones it deletes.

**Binary data.** BEAM has no mutable byte array, so the bytes of an `ArrayBuffer` live in an `atomics` array of unsigned 64-bit words, little-endian, off the process heap. Its slots are `{Data, ByteLength, MaxByteLength}`, where `Data` is `detached` after `transfer` and `MaxByteLength` is `none` for a fixed length. A typed array's slots are `{Kind, Buffer, ByteOffset, Length}`, with `Length` `auto` when it tracks a resizable buffer. `buoy_heap` hands each numeric key of a typed array (an index or another canonical numeric string) to `buoy_ref_typed_array`, as the integer-indexed exotic object requires. A buffer holds at most 1 GiB.

**Shared memory.** A `SharedArrayBuffer` keeps its bytes in the same kind of `atomics` array, and its structured clone keeps the array, so the realms that receive it share the bytes. A write of part of a word is a compare-and-swap, so it keeps what another realm writes to the rest of the word. `Atomics.wait`, `Atomics.waitAsync`, and `Atomics.notify` use the waiter lists of `buoy_ref_waiters`: one process for the VM, which keys each list by the array and the byte index, and whose order of requests is the critical section of ECMA-262 §25.4.3. A notify sends `{'$buoy_atomics_wake', Tag}` to each waiter that it removes, oldest first. A sync wait blocks the realm process in a receive. An async wait settles its promise in a job when its wake message or its timeout arrives, and, as in Node, a pending async wait does not keep a realm alive. Before a realm without work ends, it takes the messages that have already arrived, such as the wake of a wait that the realm notified itself.

**Dates.** A date object holds its time value, an integer or `'NaN'`, in its slots. `buoy_ref_tz` reads the TZif data of the zone in `TZ`, or of `/etc/localtime`, so local time has the zone's historic offsets, and the POSIX rule of the file's footer gives the offsets after its last transition. As V8 does, `toString` names the zone's standard or daylight time, and outside 1970 to 2038 it decides daylight time in an equivalent year.

**Temporal.** Buoy runs temporal-polyfill 1.0.6 (MIT, fullcalendar/temporal-polyfill), vendored unchanged in `runtime/vendor/temporal-polyfill/global.js`. `crates/buoy-cli/build.rs` edits its text and compiles it with `buoy_compiler::compile_eval` into the runtime module `buoy_temporal`: strict eval code that reads `Intl` and `nowNanoseconds` from its `this`, and whose value is the `Temporal` namespace. The edits drop the function that wraps the script. Eval code lowers like a function body, so the top-level functions of the polyfill become closures in its `'__eval__'/3`, which `buoy_ref_temporal` calls with the empty scope and context. They also read the clock from `nowNanoseconds`, which returns `erlang:system_time(nanosecond)`, and end with the namespace in place of the writes to `globalThis`, `Intl`, and `Date.prototype`. The global `Temporal` is the lazy intrinsic `'Temporal'`: its first read in a realm runs `buoy_temporal` in that realm (`buoy_ref_temporal:load/1`), and a realm that never reads it pays nothing. `Intl` is not a global. `buoy_ref_temporal` gives the polyfill the part of `Intl.DateTimeFormat` that it uses, in the en-US locale: `resolvedOptions` with the system zone or the primary identifier of a named zone, `formatToParts` with the wall-clock fields of an instant in a zone, and `format` for `toLocaleString`, which prints the default fields and ignores the styles. `buoy_ref_tz:named/1` resolves a zone identifier in any case through the zones and links of `tzdata.zi`, and `buoy_ref_tz:offset_in/2` reads the TZif file of the zone. `Date.prototype.toTemporalInstant` constructs the `Temporal.Instant` of the realm. The functions of `buoy_temporal` are built-in functions, so `Function.prototype.toString` gives them the native form. The 8 test262 tests of Temporal that fail also fail on Node 25.9 with the same polyfill (`docs/design/engine-progress.md`).

### 17.4 Functions

A function value carries its Erlang fun, so a call needs no heap read. Every function the compiler makes gets a record with its `name`, its `length`, and the place of its source text, from `buoy_ref_class:method/5`. The name of an anonymous function comes from NamedEvaluation (ECMA-262 §8.4.5): its variable, its property key, or its parameter, and SetFunctionName computes it from the key at run time. The kind decides the rest:

- `method`, `get`, `set`, and `arrow`: no `prototype`, and no construct.
- `normal`: a `prototype` object, and new can construct it. The slots hold `kind => normal`.
- `normal_nt`: a normal function that reads `new.target`. It compiles to `fun(This, Args, NewTarget)`, and its record holds a `construct` fun that passes new.target.
- `sloppy`: a normal function of sloppy code, with own `caller` and `arguments` properties, as V8 gives it. `arguments` is `null`, as in V8 outside a call. `caller` is `undefined`: the engine keeps no stack of callers, and `undefined` is what test262 takes from an engine without the extension (ECMA-262 §17.1).
- `generator` and `async_generator`: the function compiles to a maker, `fun(SelfId) -> fun(This, Args) end`, so that its body finds its own `prototype` for the generators it makes. Its `[[Prototype]]` is `%GeneratorFunction.prototype%` or `%AsyncGeneratorFunction.prototype%`, and there is no construct.
- `async`: no `prototype`, no construct, and the `[[Prototype]]` `%AsyncFunction.prototype%`.

A module-level function declaration is `{'$f', {Form, Module, Name, Length}, Fun}`: `Form` is `fn`, `fn_nt` for one that reads `new.target`, `async`, `generator`, or `async_generator`. A normal function of sloppy code is `{'$f', {fn, Module, Name, Length, sloppy}, Fun}`. Each realm makes the record of its form on first use. The name of a function expression is a cell inside it that holds the function once it exists, and so is the callee of the mapped arguments object of a sloppy function.

A bound function holds `kind => bound` and its target. A class holds `kind => class` and the fun of its `[[Construct]]`. A class is made where its code runs: a class expression or a class in a function each time, a module-level class once per realm. Each evaluation makes new private names. `this` of a derived constructor is a cell that `super(...)` binds once, and `super(...)` constructs the `[[Prototype]]` of the class. A builtin of realm 0 is the same term in every process, so its identity holds across actors. A builtin that `buoy_ref_realm:builtin/4` or a `{Name, Length}` entry of `?METHODS` makes has its own `name` and `length` properties.

**Strict and sloppy code.** TypeScript runs as ES modules, which are strict, as Node runs a package of `"type": "module"`. A JavaScript script is sloppy unless a directive makes it strict, and the compiler reads the strictness of each function from oxc. Sloppy code differs in four ways: a function called with `this` undefined or null sees the global object (`buoy_ref:sloppy_this/1`); a failed write or delete does nothing (`buoy_ref:sloppy_set/3`, `sloppy_delete/2`); a function with simple parameters gets a mapped arguments object whose `callee` is the function; and an assignment to an undeclared name creates a property of the global object (`buoy_ref_realm:set_global/3`). Strict code resolves an undeclared name before the right side of an assignment runs (`buoy_ref_realm:has_binding/1`), and `buoy_ref_realm:set_resolved/3` throws a ReferenceError when the name was unresolvable then. In a `with` statement, whose object is the ToObject of its value, a name that no declaration inside it binds resolves through the object first: `buoy_ref:with_has/2` tests the property and `Symbol.unscopables` once for each read, write, call, `typeof`, and `delete`. `buoy_ref:with_get/3` and `with_set/4` then test the property again, as GetBindingValue and SetMutableBinding do, so strict code throws a ReferenceError when it is gone, and a compound assignment or an update reuses the one resolution.

**Bindings read early.** A `let`, `const`, or class that code reads before its declaration, such as a hoisted function declaration or an earlier statement, gets its heap cell at the start of its block, holding `'$uninitialized'`; so does a parameter that an earlier default reads, a binding of a `for` head that its right side reads, and a class binding that its `extends` clause reads. The declaration writes the cell, and a read before that throws a ReferenceError (`buoy_ref_class:initialized/2`). A module-level `let` or `const` holds `'$tdz'` in the process dictionary until the top-level code declares it. A read of a binding whose declaration has not run in the same function throws the same error (`buoy_ref:tdz_error/1`).

**The global object.** `{'$o', globalThis}`, or `{'$o', {N, globalThis}}` in the realm N, holds every global binding as a writable, configurable, non-enumerable property, except `undefined`, `NaN`, and `Infinity`, which are read-only and non-configurable. A name that no scope declares reads the global object and its prototype chain (`buoy_ref:global/1`). The top-level `var` names and functions of a script are properties of the global object, and its top-level `let`, `const`, and classes are bindings of the global declarative record of the realm: a map in the process dictionary, one for each realm, from each name to the key of its module variable and its mutability. `buoy_ref_realm:declare_script/4` declares both before the code runs (GlobalDeclarationInstantiation). It throws a SyntaxError for a lexical name that the record holds or that is a non-configurable property of the global object, such as `undefined`, and for a `var` name or function that the record holds, before it declares anything. A name that no scope declares reads, writes, deletes, and tests with `typeof` the record before the global object, so other scripts, eval code, and modules see the lexical bindings of a script. The top-level `this` of a script is the global object.

**eval and the Function constructor.** The VM keeps one `$BUOY_COMPILER compile-eval --serve` process, a hidden command of the Buoy binary, behind a port that the registered process `buoy_eval_compiler` owns. `buoy run` and the test262 runner set `BUOY_COMPILER`. Each request is a frame of `{packet, 4}`: the options `[--strict] [--function] [--script] [--place=P] [--private=a,b] [--lexical=a,b] [--scope=a,b]` and the module name, one on each line, then an empty line and the source text. The answer is a status byte and a text: 0 and an Erlang module, or 2 and `<ErrorName>\t<message>`. The server process compiles the module without the optimizing passes and loads it, once per source text and options in a VM. The module's `'__eval__'/3` runs the code in the calling realm with a `this`, a scope, and a context map, and returns its completion value. Each expression statement sets the completion value, and `if`, the loops, `switch`, `try`, `with`, and a catch clause reset it to undefined first, as `UpdateEmpty` does. A source text that is only white space and comments, after an optional hashbang comment, evaluates to undefined, and one regular expression literal evaluates to a new RegExp, without a module. With `--script`, the source text compiles as a classic script of its own, and `buoy_ref_eval:script/1` runs its `'$body'/0` in the calling realm and returns its completion value: the `$262.evalScript` of a test262 host. The `this` of a script is the global object of its realm.

A direct eval passes the scope of its call innermost first: `{Name, Cell}` for each local binding in a heap cell, which the analysis makes of every binding that a direct eval can see, with the arguments object in a cell after the bindings of its function (the cell of the `arguments` binding itself when sloppy code of the function assigns `arguments`), and an immutable binding, such as the name of a function expression, as a copy whose name starts with `!`, which strict eval code may not write, `{<<"@with">>, Object}` for each `with` statement, and `{<<"@vars">>, Object}` for each sloppy function that calls eval directly. Such a function makes that object, `buoy_ref_eval:var_object/0`, at its start, and its code resolves names through it as through a `with` object around its body, except that a call of a function that the object holds gets undefined as `this`. Eval code resolves each name that it does not declare through the scope: through the objects in front of the first binding of the name, then that binding, then the global declarative record and the global object. A direct eval inside eval code passes its own scope, then the scope of its caller. The context map holds what the place of the call gives the code (PerformEval), and `--place` names it: `function` gives `new_target`, `method` also `home` for `super.x`, `field` marks a class field initializer, where `arguments` is a SyntaxError, and `constructor`, in a derived constructor, also `this_cell`, `class`, and `init` for `super(...)`. `privates` lists the private names that the call sees as `[{Name, Key}]`. The compiler drops the early errors of `super`, `new.target`, and private names that the place permits, outside the functions of the eval code. Strict eval code keeps its `var` names and functions as locals, and so does any eval code with its `let`, `const`, and classes. A `var` name or a function of sloppy eval code that the caller's function binds is that binding. Any other one is a deletable binding of the first `@vars` object (`buoy_ref_eval:declare_vars/3`), or, without one, a configurable property of the global object, after `buoy_ref_realm:declare_globals/3` checks that each name can be declared and that the global declarative record does not hold it. Sloppy eval code may not declare with `var` a name that a lexical binding between the call and its function's variables holds, or, in a parameter default, a parameter or `arguments` (`--lexical`): that is a SyntaxError. The Function constructor and the constructors of the other function kinds build `(function anonymous(...) {...})` and check that the body does not close the function early (`--function`).

### 17.5 Property keys

A property key is one of these terms:

- an array index, `0 =< K =< 2^32 - 2`, as an integer;
- any other string, as a string of section 17.1;
- a symbol;
- a private name, `{'#', Unique, Name}`, with a unique integer for each evaluation of the class body that declares it. A private element is in the `Props` of its object under its name, and reflection never returns it: a field holds its value, a method `{'$method', F}`, and an accessor `{'$accessor', Get, Set}`.

ToPropertyKey turns a canonical numeric string such as `"7"` into the integer, and a number into its string, so `o[7]` and `o["7"]` are one key. `buoy_heap:own_keys/1` returns the keys in the order of OrdinaryOwnPropertyKeys: array indexes in ascending order, then string keys in the order of their creation, then symbols in the order of their creation.

### 17.8 ES modules and CommonJS

**The graph.** `reference/graph.rs` loads every module that the entry reaches through `import`, `export ... from`, `import()` of a string, and `require()` or `require.resolve()` of a string. `resolve.rs` resolves each specifier as Node 25 does: `ESM_RESOLVE` for `import` and `import()`, and `require.resolve` for `require`. The conditions are `node`, `import` or `require`, `module-sync`, and `default`. `node-addons` is left out, because Buoy loads no native addon. A symlink resolves to its real path. After Node's algorithm fails, a relative `./x.js` may name `./x.ts`, as the TypeScript compiler allows. The format of a file follows Node: `.mjs` and `.mts` are ES modules, `.cjs` and `.cts` CommonJS, and `.json` JSON. A `.js` or `.ts` file takes the `type` of its package scope, or, without one, is an ES module exactly when it has ES module syntax. When a module calls `import()` or `require()` with a computed specifier, the graph also loads each file that a relative path string of the module names, and the files of one directory that a template such as `` `./locales/${name}.js` `` matches. A specifier that the graph still does not reach, such as `require(path.join(dir, name))`, loads at run time: `buoy_module` asks the compiler process of the VM (`buoy compile-eval --serve`, a frame whose header is `@load` with the entry, the importer, the specifier, and the mode), which resolves it with `resolve.rs` and compiles the target as the entry of a program in the root of the running program, so a module that both share has one name. The VM compiles the modules that it does not hold yet and adds their paths to the graph.

A file under the project root takes its name from its path (section 2). A file outside it, such as a package in the pnpm store, takes its name from its path after its first `node_modules` directory, so the name does not depend on the machine.

**Linking.** `reference/link.rs` resolves each import by the ResolveExport and GetExportedNames algorithms of ECMA-262. An import that does not resolve, an ambiguous star export, and a missing module are errors of the importing module. The runtime throws them when it links the graph, before any module evaluates, as Node does, so a module that only a failing `import()` reaches does not stop the program. A module other than the entry that does not compile becomes a module whose loading throws its first diagnostic: a SyntaxError for a syntax error, else an Error whose `code` is the diagnostic code. In a TypeScript file, an import whose binding no value reads is erased.

**The interface of a compiled module.** `reference/linking.rs` writes these functions, and `buoy_module` calls them:

| Function         | Value                                                                                                                                                                                                             |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `'$module'/0`    | `#{kind => esm \| cjs \| json, path => Path, requests => [Module], async => boolean(), error => none \| {Kind, Code, Message}}`: `requests` are the static imports in order, `{defer, Module}` for `import defer` |
| `'$body'/0`      | An ES module: runs the top-level code, and returns a promise when it awaits                                                                                                                                       |
| `'$cjs'/0`       | A CommonJS module: the function `(exports, require, module, __filename, __dirname)`, from the file inside Node's wrapper                                                                                          |
| `'$json'/0`      | A JSON module: its UTF-8 text                                                                                                                                                                                     |
| `'$export'/1`    | The value of an exported binding: by its local name, a UTF-8 binary, in an ES module, and by its export name, a string of the engine, in a CommonJS or JSON module                                                |
| `'$namespace'/0` | `[{Name, fun() -> Value end}]`, the export names in code unit order                                                                                                                                               |
| `'$resolve'/2`   | `(Specifier, import \| require)`: `{Path, Module}`, `{Path, none}`, `{builtin, Name}`, `{error, Code, Message}`, or `none` for a specifier that the module does not name                                          |

**Bindings.** A read of an imported binding calls `Module:'$export'(Key)`, so every import is a live binding. A module variable lives under `{'$m', Module, Name}` as `{v, Value}`. Before its declaration runs, its getter `'$get_<name>'/0` throws a ReferenceError for `let`, `const`, and `export default <expression>` (the local `*default*`), and returns undefined for `var`. A top-level class is created when its declaration runs, and an import of it throws a ReferenceError before that. An assignment to an import throws a TypeError. An actor realm sets `'$buoy_actor_realm'`: there a getter runs the initializer instead, because the top-level code of the actor's module does not run in its realm. The realm evaluates the modules that the actor's module imports before it constructs the actor. `spawn` of an imported class passes `{export, Module, Key}` to `buoy_jobs:spawn_actor/2`, and the actor's realm reads the class with `Module:'$export'(Key)`.

**Evaluation.** `buoy_module` keeps the record of each module of a realm under `{'$buoy_module', Module}`. `run/1` links the graph from the entry, then evaluates it with the Evaluate algorithm of ECMA-262 (16.2.1.5.3), with top-level await: a module that awaits, and each module that waits for one, evaluates when its dependencies finish, in the order of `[[AsyncEvaluationOrder]]`. An error of a graph that does not await throws as an uncaught exception. For a graph that awaits, `run/1` returns the evaluation promise, and `buoy_jobs:run_main/1` prints Node's warning and exits with status 13 when the promise never settles.

**`import defer`.** A deferred import, `import defer * as ns`, links its module but evaluates only the modules with top-level await that it reaches (GatherAsynchronousTransitiveDependencies of the proposal). `ns` is a heap record of class `deferred_namespace`, whose `Symbol.toStringTag` is `"Deferred Module"`. The first use of a string key other than `"then"` evaluates the module synchronously, or throws a TypeError when the module or a module that it imports awaits or is evaluating (`buoy_module:ensure_deferred/1`). `import.defer(specifier)` resolves to the deferred namespace once the modules with top-level await have evaluated.

**Namespaces.** A namespace object is a heap record of class `namespace` with a null prototype. Each export is a property `{'$live', Fun}`, writable, enumerable, and not configurable, and `Symbol.toStringTag` is `"Module"`. `buoy_heap` reads a live property by calling `Fun`. A write throws a TypeError, and `buoy_module:define_namespace/3` lets `Object.defineProperty` succeed only when it changes nothing.

**`import()` and `import.meta`.** `import(specifier, options)` calls `buoy_module:dynamic_import/4`. It converts the specifier with ToString, checks the options, and resolves the specifier with `'$resolve'/2`, or else among the files of `'$graph'/0`. In a later microtask, as Node loads asynchronously, it links and evaluates the module, and the promise resolves to the namespace. A source phase import, `import.source()`, rejects with a SyntaxError. `import.meta` is an object with a null prototype and the properties of Node 25: `dirname`, `filename`, `main`, `resolve`, and `url`.

**CommonJS.** `require` resolves with `'$resolve'/2`, or else among the files of the graph for a path that the code computed. A CommonJS module runs once per realm through `require.cache`, an object with a null prototype keyed by filename. The Module object holds `id`, `path`, `exports`, `filename`, `loaded`, `children`, `paths`, and `require`, and the wrapper function runs with `this` as `module.exports`. An ES module that imports a CommonJS module evaluates it at its place in the graph and reads a snapshot of `module.exports` taken after it ran. `default` and `'module.exports'` are `module.exports`, and each name that the compiler finds as Node's cjs-module-lexer does is a property of it: `exports.x =`, `module.exports.x =`, `Object.defineProperty(exports, 'x', ...)`, the keys of `module.exports = { ... }`, and the names of a module that `module.exports = require(...)` or `__exportStar(require(...))` re-exports. `require` of an ES module returns its namespace, or its `'module.exports'` export when it has one. With a default export and no `__esModule` export, the namespace also has `__esModule: true`, as in Node. A graph that awaits throws `ERR_REQUIRE_ASYNC_MODULE`. The default export of a JSON module is its parsed value.

**Built-in modules.** A `node:` specifier, or the bare name of a built-in module of Node, resolves to `{builtin, Name}`. `buoy_module:builtin_namespace/1` returns the value of the module. `node:module` provides `createRequire`, `builtinModules` (the list of Node 25.9.0), and `isBuiltin`. Every other built-in module is Node's own JavaScript, which `buoy_node` runs ([node-builtins.md](node-builtins.md)): `buoy_node:require/1` returns `module.exports` from Node's `BuiltinModule` loader. A built-in that the runtime does not hold throws an Error with the code `ERR_BUOY_BUILTIN`.

**Node's bootstrap.** The first use of a built-in module, or of a global of Node that the engine does not define (`process`, `Buffer`, `global`, `setImmediate`, and `clearImmediate`, each an accessor of the global object until then), runs Node's bootstrap in the realm (`buoy_node:ensure/0`). From then on the realm runs the event loop of Node (`buoy_node_loop`): after each job, the microtasks and the tick callback; the timers and immediates of `lib/timers`; the rejection callback of `internal/process/promises`; an uncaught exception through `process._fatalException`; and Node's exit rule. When no ref'd timer, immediate, or handle is left, the realm emits `'beforeExit'`, runs again if that queued work, emits `'exit'`, and ends with `process.exitCode`, or 0. A realm that never uses Node keeps the job loop of section 17.4 alone.

**Tests.** `tests/reference/module-graph.ts`, `module-commonjs.ts`, `module-require.ts`, and `module-dynamic-import.ts` import the modules of `tests/reference/modules/`, and `npm-packages.ts` imports five packages of `tests/node_modules`. The test262 directories `test/language/module-code`, `test/language/import`, `test/language/export`, `test/language/expressions/dynamic-import`, and `test/language/expressions/import.meta` cover the language. `crates/buoy-compiler/src/resolve.rs` tests the resolution of `exports`, `imports`, patterns, and `main`.

### 17.9 Regular expressions

The engine matches regular expressions in Erlang, with the semantics of ECMA-262 22.2, and does not use the PCRE library of OTP `re`. PCRE reads Latin-1 or UTF-8, so it cannot hold a lone surrogate. It also differs from JavaScript in the captures of a repeated group, the empty check of a quantifier, and a backreference to a group that has not matched. Bun runs JSC's Yarr, and Boa runs regress: both are backtracking engines of their own, and Buoy follows them.

- `buoy_regexp_syntax` parses a pattern with the grammar of 22.2.1, the extensions of Annex B.1.2 for a pattern without `u` or `v`, and the early errors. It reads code points with `u` or `v` and code units without them.
- `buoy_regexp_match` compiles the tree into the Matcher closures of 22.2.2 and runs them. A Matcher is `fun(Input, Index, Captures, Continue)`, and a failure returns `false` to the last choice point. A node without choice points, such as a character, a class, a literal, or an assertion, compiles to a step `fun(Input, Index) -> Index | false`. A quantified step backtracks in a loop, so a long run does not deepen the stack. Indexes count code units in every mode, and with `u` or `v` a surrogate pair is one character. Without the `y` flag, the scan skips to the next place where a match can start: an occurrence of the literal prefix, found with `binary:match/3`, or a character that the first node of the pattern accepts.
- `buoy_regexp_charset` holds the CharSets as sorted range lists, the class escapes, the properties, and the case mappings. With `i`, a class compiles to its closure under Canonicalize, so the matcher tests membership only. A large set compiles to a binary of 24-bit bounds, because the collector of the heap scans funs term by term and a binary is one term.
- `buoy_regexp_unicode` holds the Unicode data: the properties of Tables 65, 66, and 67, simple case folding, and the uppercase mapping of a BMP pattern. `scripts/regexp-unicode.escript` writes it from the Unicode Character Database, at the version that the test262 property escape tests name.
- `buoy_ref_regexp` holds `RegExp`, `RegExp.prototype`, the RegExp String Iterator, the legacy static properties such as `RegExp.$1`, and the six methods of `String.prototype` that take a pattern. A RegExp object has the class `regexp`. Its slots hold the source, the flags, the group names, and `legacy`, which is true when `RegExp` itself made the object. The slots do not hold the matcher: each realm keeps the matchers it compiled in its process dictionary, keyed by source and flags, so many objects share one matcher, the collector scans it once, and a literal in a loop compiles once.
- The protocols of Symbol.match, Symbol.replace, and Symbol.split follow the spec step by step, with one exception. When a RegExp is pristine, so reading it runs no user code, they call the matcher directly: its prototype is `RegExp.prototype`, its only own property is a numeric `lastIndex`, and the realm has not written to `RegExp.prototype` (or, for split, to `RegExp`). An intrinsic that a realm has not written has no entry in its heap (section 17.2), so `exec`, `flags`, and the flag accessors are the builtins, and the result is the same.

The compiler lowers a regular expression literal to `buoy_ref_regexp:literal/2`, which makes a new object each time it runs. The parser of oxc checks the pattern of each literal, so an invalid literal is a `BUOY200` diagnostic, as an early error must be.
